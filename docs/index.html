How it works

Your app answers HTTP. ARK does the rest.

Every message takes the same path, and every step has one clear outcome you can see.

Point it at a topic

Describe a pipeline in YAML: source topic, your endpoint, where results and failures go.

ARK checks and calls

Data rules validate each message, routing rules can skip the call, and ARK POSTs the rest with a stable correlation ID.

Results land in Kafka

Answers go to the result topic, bad data to the reject topic, failures to the dead-letter topic, each with the reason.

Your app answers 2xx
The answer is produced to the destination topic, then the offset is committed.
Your app answers 4xx
The message is the problem, not the app: it goes to the reject topic with the reason, no retry.
429, 425 or 408
"Come back later": ARK waits, honoring Retry-After, and tries again without spending a retry.
5xx or a timeout
Retried with backoff, then dead-lettered with the reason. You can browse and retry it later.
Your app is down
The circuit breaker opens, messages wait safely in Kafka, and ARK resumes the moment the health check passes.
ARK crashes mid-message
Nothing was committed past it, so it is delivered again with the same correlation ID.
Features

Everything a Kafka consumer should have, already done.

Built and tested against a real broker: crashes, rebalances, dead apps, bad data.

Delivery you can trust

At-least-once with in-order commits. A stuck message is retried in place, never skipped. Order is kept per key.

Data rules

Required fields, types, ranges, patterns, enums, formats, size, unknown fields, keys and headers. Bad data never reaches your app.

Rules without code

Route before or after the callback with simple conditions: auto-approve small orders, send big ones elsewhere.

Dead letters you can act on

Browse, retry or discard with the reason attached. Redrive on a schedule. Handled stays handled across restarts.

Protects your app

Concurrency limits, a circuit breaker with health probes, backpressure on 429, and load balancing across backends.

Cluster on Kafka itself

Shared config, cluster-wide pause, label-based placement and fast failover. No etcd, no ZooKeeper, nothing new to run.

AI assistant over MCP

Ask what is happening and why, explain an error, find weird data, tune throughput, draft pipelines you approve first.

Secure by default

Viewer, operator and admin tokens for the API and for MCP, per-pipeline AI access, and an audit log for every change.

See everything

Prometheus metrics for throughput, latency, lag, oldest uncommitted age, breaker state and every rule match.

Quick start

From zero to flowing in two minutes.

All you need is Docker. The demo starts Kafka, ARK, and a tiny app that echoes what it receives.

01

Start it

Kafka, ARK and the demo app, with one pipeline from orders.raw to orders.processed.

shell
git clone https://github.com/raven-clown/ark.git && cd ark
docker compose up -d --build
02

Send three orders

A good one, one that breaks a data rule, and one the app fails on.

shell
printf '%s\n' \
  '{"order_id":"A1","amount":10}' \
  '{"order_id":"A2","amount":-5}' \
  '{"order_id":"A3","amount":7,"fail":true}' \
| docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
    --bootstrap-server localhost:9092 --topic orders.raw
03

See where each went

A1 is processed, A2 is rejected with the broken rule, A3 is dead-lettered after 3 tries. Every one carries its reason.

shell
topic() { docker compose exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --from-beginning --timeout-ms 5000 \
  --property print.headers=true --topic "$1" 2>/dev/null; }

topic orders.processed   # A1, with the app's answer
topic orders.rejected    # A2: amount is -5, below the minimum 0
topic orders.dlq         # A3: answered status 500, 3 attempts
04

Ask ARK

Over the REST API, or from any MCP client in plain language.

shell
curl -s localhost:8080/api/v1/pipelines/orders/dlq \
  -H 'Authorization: Bearer demo-admin-token'

claude mcp add --transport http ark http://localhost:8080/mcp \
  --header "Authorization: Bearer demo-mcp-token"
Configuration

One pipeline, one block of YAML.

No code, no framework. Change it and reload: an invalid config is refused before it touches anything running.

  • Required dead-letter topic. A message always ends up somewhere you can see it.
  • Scale with one number. workers splits partitions inside one process, or across a cluster.
  • Your timezone. Every time ARK shows you is ISO 8601 in the zone you set.
config.yaml
brokers: [kafka:9092]
timezone: Asia/Bangkok

pipelines:
  - name: order-processor
    source_topic: orders.raw
    destination_topic: orders.processed
    dead_letter_topic: orders.dlq
    reject_topic: orders.rejected
    consumer_group: order-processor
    workers: 3

    target:
      url: http://order-app:8080/process
      health_check_url: http://order-app:8080/health
    retry: {max_attempts: 3, backoff_ms: 1000}

    data_rules:
      on_violation: reject
      fields:
        - {path: order_id, required: true, type: string}
        - {path: amount, type: number, min: 0}

    fast_path_rules:
      - name: auto-approve-small
        condition: "data.amount < 100"
        action: pass_through
AI assistant

Ask your pipelines what's wrong.

ARK speaks MCP, so any AI client and any model can operate it. It works out what you mean first, asks back when something is unclear, and answers from real data, never guesses.

  • What, why, what to do. Diagnoses come with the evidence and the next step.
  • Finds weird data. Samples real messages, spots odd fields and outliers, and drafts rules to catch them.
  • Changes need your OK. Every config change is a preview and a diff first, applied only after you confirm.
  • Least privilege. Read-only, operator or admin tokens, and a per-pipeline limit on top.
